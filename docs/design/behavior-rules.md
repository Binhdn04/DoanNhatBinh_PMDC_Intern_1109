# Cross-document behavior rules

This is the normative refinement of [requirements](../requirements/requirements.md) and [specification](../requirements/spec.md) for the audit corrections. [OpenAPI](../api/openapi.yaml) defines the wire contract; [database design](../database/database-design.md) defines persistence. These rules are implementation decisions, not claims of implemented behavior. [Traceability](./traceability.md) supplies acceptance scenarios.

## Identity and supervisor assignments

`GET /api/v1/me` supplies permitted roles. `PUT /api/v1/me/active-role` validates the selected role against current `user_roles`, updates the current authenticated session under a row lock, and returns identity plus a replacement bearer token. A JWT contains user ID, session ID (`sid`), active role, session version, and expiry. Every protected request validates the session, version, expiry, current role membership, and current record relationship. A role change increments session version; tokens issued for its prior version are invalid. Selecting the current role returns a valid token without a version increment. Sign-in must provision that session, although the sign-in UI remains outside scope. Losing the switch response requires normal session reauthentication; a stale token cannot switch again. The client replaces its token, clears role-scoped caches, cancels old requests, and opens the new role's landing page only after success. Other browser tabs discard stale state on 401.

Company Staff for the application's company or Admin selects the initial supervisor during acceptance. `GET /api/v1/supervisors?applicationId=...` returns paged IDs, names, and departments, filtered by optional name search. Eligible users hold SUPERVISOR and have a supervisor profile; v1 imposes no company/program restriction. Eligibility is checked again inside acceptance. Students and Supervisors cannot use this directory. Admin may instead supply `placementId` when managing an assignment; exactly one context is required.

Only Admin may later assign, replace, or revoke the supervisor of an Active placement, through its operational detail screen. The command contains `expectedAssignmentId` (null when unassigned), `supervisorUserId` (null to revoke), and a nonblank reason. Lock the placement, compare expected assignment, recheck eligibility, revoke the prior row and insert any replacement in one transaction with an audit event. Same current supervisor is a no-op; a stale expectation returns 409. Retain original assignment actor/time plus revocation actor/time/reason. A revoked-only placement is temporarily unassigned: Student/company access continues and Admin handles reviews until reassignment. Terminal placements permit assignment history reads but no assignment changes. Assignment checks on every request immediately deny a removed supervisor's future access, including documents and AI polling.

## Application completeness and acceptance replay

Application contact name/email, university, major, availability, cover note, and AVAILABLE owned CV are mandatory. Trim required strings and reject empty/whitespace-only values with 400 field errors. Optional phone, graduation year, and supporting documents remain optional. Profile edits never rewrite a submitted application snapshot.

Acceptance requires `supervisorUserId`, `startDate`, `endDate`, and optional note. End date must not precede start date. Staff/Admin uses the eligible-supervisor lookup before confirming acceptance. Lock the application first. On INTERVIEW, recheck actor and supervisor, then atomically write ACCEPTED, immutable history with the canonical command, one placement, initial assignment, reporting periods, and one Student notification. On ACCEPTED, compare the original retained supervisor/date/note command, with absent/blank note normalized to null. An identical replay returns 200 and the existing placement link with no new writes; different input returns 409 `ACCEPTANCE_CONFLICT`. Reassignment does not alter the retained command. Other terminal transitions are rejected. Unique placement application ID and an accepted-history uniqueness constraint backstop concurrent writes; they do not replace the replay comparison.

## Skill identity, scoring, and relevance

`GET /api/v1/students/me/skills` and replacement PUT return canonical `skills.id`, display name, and optional proficiency. Normalize skill names using Unicode NFKC, trim, collapse Unicode whitespace runs to a single ASCII space, and Unicode lowercase with no locale-specific rules. The unique normalized name resolves the same canonical skill ID across student/posting input. Reject duplicate normalized names within a request, including a posting skill repeated across required/optional groups. Return matched/missing names sorted by normalized name, then canonical ID. Proficiency is retained for display but does not change v1 score.

Publishing requires an explicitly supplied `skills` collection, which declares both groups through each entry's importance. Empty required and optional groups are valid, including `skills: []`; omitted skills on a new draft means not yet declared and fails publication. All other mandatory publication fields remain required. A missing skills property during later edits preserves the previously declared collection.

For calculation version `skill-v1`, each required skill has weight 2 and each optional skill weight 1. Let D be the sum of all posting-skill weights and M the sum of weights whose canonical IDs occur in the student's skill set. If D > 0, score is `floor(100 * M / D + 0.5)` (round halves upward). If D = 0, score is 0, matched and missing lists are empty, and reason is `NO_POSTING_SKILLS`; display “No skills specified; score is not an assessment of suitability.” Otherwise reason is `SKILL_OVERLAP`. A student with no skills receives 0 and all posting skills as missing when D > 0. No synonym inference, proficiency weighting, AI, or preferences influence the score.

| Required | Optional | Student skills | M / D | Score | Matched / missing |
| --- | --- | --- | --- | --- | --- |
| Java | SQL | Java | 2 / 3 | 67 | Java / SQL |
| Java | SQL | SQL | 1 / 3 | 33 | SQL / Java |
| Java | SQL | Java, SQL | 3 / 3 | 100 | Java, SQL / none |
| Java | SQL | none | 0 / 3 | 0 | none / Java, SQL |
| none | SQL | SQL | 1 / 1 | 100 | SQL / none |
| none | none | Java | 0 / 0 | 0 | none / none; NO_POSTING_SKILLS |
| A, B, C, D | none | A | 2 / 8 | 25 | A / B, C, D |
| A, B, C | D, E | D | 1 / 8 | 13 | D / A, B, C, E |

Keyword search filters by case-normalized substring in title, company name, or skill names. All nonempty whitespace-separated query tokens must match at least one of these fields. Explicit filters use AND. For relevance, count matching preference dimensions (0–4): company industry in preferred industries, posting location in preferred locations, work arrangement in preferred arrangements, and duration within every supplied min/max bound (inclusive). An unset dimension contributes zero. Industry/location comparison uses the same text normalization as skill names. Order relevance by this count descending, then score descending, publishedAt descending, and ID ascending. Order match_score by displayed score descending, then publishedAt descending and ID ascending. Order newest by publishedAt descending and ID ascending. Default sort is relevance. Preferences never filter candidates; empty preferences still yield a stable ordering.

## Reporting calendar and deadlines

Use validated IANA timezones. Resolve term timezone override, else the term's program timezone, else `Asia/Ho_Chi_Minh`. A posting without a term uses the fallback. Snapshot that resolution into posting.deadline_timezone at creation and placement.reporting_timezone at acceptance. Later configuration edits do not move those snapshots. Task “today” uses placement timezone; application eligibility uses posting timezone. A date deadline remains valid until the next local day's start, exclusive; API returns that instant as dueAt where relevant.

Acceptance materializes immutable `reporting_periods` for each Monday–Sunday week overlapping the inclusive placement date range. First/last partial weeks use those full canonical week boundaries; students report only placement activity within them. Each period is due at the next Monday 00:00 in placement timezone, converted to UTC. The local Sunday is its displayed dueDate. For unusual timezone transitions, a nonexistent boundary resolves to the first valid instant after the gap and an ambiguous boundary to the earlier instant. The reporting-period ID, not user-selected arbitrary dates, identifies the week. Placement dates cannot be edited in v1. `GET /placements/{placementId}/reporting-periods` exposes weeks and due times even when there is no report; the UI cannot start a future week before its Monday. Past-due submission is allowed while the placement is Active and does not erase lateness. Ending a placement stops reminders and draft/submission/review writes, retaining calendar and history.

For a placement from Wednesday 2026-09-16 through Tuesday 2026-09-22 in Asia/Ho_Chi_Minh, periods are September 14–20 (due `2026-09-20T17:00:00Z`) and September 21–27 (due `2026-09-27T17:00:00Z`). Due times are exclusive cutoffs. A period with no submitted version at or after dueAt is missing/late even if a private draft exists; a submitted version's submittedAt determines whether its initial submission was late. Revision requests retain the original deadline and do not create a new reminder obligation. Monitoring derives these facts from periods and submitted versions without exposing draft content.

The API Notifications module runs an internal scheduler every 60 seconds, independently of optional AI. It queries Postings and Placements application interfaces, not their private repositories. Each API replica may scan; unique notification dedupe keys arbitrate concurrent insertion. No public scheduler endpoint exists. Each scan checks current eligibility and inserts missing reminders transactionally:

| Reminder | Recipient and condition | Window | Dedupe key |
| --- | --- | --- | --- |
| Application closing | Student who saved the eligible posting and has never applied | `[dueAt - 24h, dueAt)` | recipient + posting ID + dueAt + APPLICATION_DUE |
| Report due | Placement Student on Active placement; no submitted version for that period | `[dueAt - 24h, dueAt)` | recipient + period ID + REPORT_DUE |
| Report overdue | Same Student, still no submitted version | `[dueAt, infinity)` while Active | recipient + period ID + REPORT_OVERDUE |

Scans recompute all currently eligible windows, so restarting does not depend on an in-memory cursor. Expired application/upcoming windows are not backfilled; overdue-report reminders are caught up. No repeated daily overdue alerts. Source lifecycle/submission changes and scheduler inserts coordinate using source row locks through module interfaces and a shared transaction. A concurrent save/application/submission is serialized at the decision point; already-issued notifications remain historical records. Reminders deep-link to a posting or placement with reportingPeriodId even when a report does not yet exist. Monitoring reads the same calendar; it never invokes a mutation. Scheduler errors log scan age and retry next minute; deployment health flags scans older than five minutes.

## Private reports, attachment persistence, and version review

Draft saves atomically replace draft text and `report_draft_documents`, and set draft_saved_at even when saved text is empty. The period must belong to the placement, must have started, and cannot change after creation. Only one report aggregate exists per period. Referenced documents must belong to the Student and be AVAILABLE. Draft links block deletion. Submission locks placement/report, validates all three nonblank text fields and attachments, appends one immutable version, copies attachment links to `report_version_documents`, advances current version, clears draft fields/links and draft_saved_at, and changes state to SUBMITTED. Historical links keep files retained.

Revision editing leaves state REVISION_REQUESTED. The first revision save receives the student's edited prior-version content and full attachment selection; it creates private draft state without changing any submitted version. Reloading before that save may use the last submitted version as the editor's starting content. The API `draft` property is present only for the owning Student with saved draft data. Admin, Supervisor, and Company Staff never receive draft text or draft attachment IDs, even after an earlier submission. Before the first submission, their lists omit the report and detail returns 404. Reporting-period projections use MISSING and omit reportId for those viewers until a version exists. Authorized submitted-history reads remain available after lifecycle closure.

Each review command contains reportVersionId and each review response retains it. Under placement/report locks, require an Active placement, SUBMITTED state, and that exact current version, then insert one review (unique version ID), change state, and notify the Student atomically. A stale/already reviewed version returns 409 `REPORT_VERSION_CONFLICT` without writes; no decision is automatically replayed against a newer version. Revision feedback must be nonblank (400 otherwise). UI preserves feedback on conflict, refreshes the report, and requires the reviewer to inspect/reconfirm the new version. Prior reviews join to their versions by ID, not array position.

## API-mediated file transfer

The browser never contacts object storage. Creating upload metadata returns an absolute same-origin `/api/v1/documents/{id}/content?transferToken=...` URL and expiresAt five minutes after issuance. The API signs a token bound to session, document, PUT method, declared media type, byte count, and SHA-256. Browser sends bytes with its bearer token through the reverse proxy to the API; the API streams into private storage. Maximum size is 10 MiB; accepted formats are PDF, JPEG, PNG, DOCX, validated by content signature as well as declared metadata. `/complete` verifies size, digest, and format before AVAILABLE; mismatches become REJECTED. AVAILABLE completion retries return the same document; uploads cannot overwrite AVAILABLE content. An expired upload authorization requires a new upload record, leaving the prior PENDING record for cleanup after 24 hours.

Download-url returns a five-minute GET token bound to session and document. Every content request rechecks session version and current owner/linked-record permission, so revocation is effective even for an unexpired URL. Expired/invalid transfer tokens return 403. Browser uses authenticated fetch and a local blob download; navigating directly without bearer authentication is insufficient. No storage key or signed storage URL is exposed. Proxy and API logs redact transferToken; content responses use private/no-store caching and safe attachment disposition. Proxy request limits allow a 10 MiB stream; database and storage have no public ingress. The Documents adapter provides put/get/verify methods, not browser storage URL signing.

## Durable advisory AI inputs and recovery

On request, the API authorizes the current source and reads it in one repeatable-read transaction, then persists an immutable minimized input_snapshot before returning 202. Match input includes requester/source IDs for internal identity, calculationVersion, deterministic score/reason, normalized required/optional and matched/missing skills; no contact details, CVs, or unrelated profile data. The worker sends only the score and skill content to the provider, not internal IDs. Report requests explicitly identify reportVersionId; snapshot includes that version's three submitted text fields and version identity, excluding attachments and unrelated records. Old submitted versions can be summarized while the requester remains authorized. DTO returns postingId/calculationVersion or reportVersionId, inputFingerprint and promptVersion; never the snapshot itself. UI labels the summarized version or match snapshot and marks a match explanation stale when current source inputs differ.

Fingerprint is SHA-256 of canonical JSON (sorted object keys, stable normalized skill ordering, UTF-8) including kind, source IDs, snapshot, calculation version and prompt version. Reuse is only within the same requester/kind/fingerprint/prompt version for PENDING, PROCESSING or SUCCEEDED. A failed job can be explicitly requested again. No cross-user cache reuse. The API rechecks source access before reuse or polling; removed assignments cannot read earlier summaries. Match generation always uses the snapshot, even if live skills change later. Worker database privileges cover ai_jobs input/job/result fields only.

The API computes sourceChanged for match jobs on creation and polling by comparing current authorized matching input to the retained snapshot; the UI uses it to label stale explanations. This read never rewrites the job snapshot or generated result. Report jobs expose their immutable reportVersionId instead.

Claim due PENDING jobs using an atomic row lock with skip-locked semantics; increment attempts, assign a new claim_token and a 120-second lease. Provider call times out after 60 seconds. Success/failure writes require the same claim_token and an unexpired lease, preventing a delayed worker from overwriting a newer attempt. Each worker scan recovers expired PROCESSING leases: requeue when attempts < 3, otherwise FAILED with WORKER_INTERRUPTED. Retry transient failures after 30 seconds following attempt one and 120 seconds following attempt two; the third failed attempt is terminal. Nonretryable provider/validation errors fail immediately with safe codes. No original input is reconstructed from mutable records. Core workflows do not depend on any job completing.
